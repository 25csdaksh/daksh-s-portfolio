CHAPTER 01

Introduction to HTML

Why every website — no matter how fancy the framework — is HTML underneath.

HTML (HyperText Markup Language) is the language browsers use to understand what's on a page: this is a heading, this is a paragraph, this is a list, this is a picture. It doesn't make things pretty (that's CSS) or make things interactive (that's JavaScript) — it gives content meaning and structure.

→ Why learn HTML first?

  • Every web page — React, Vue, WordPress, plain static sites — ends up as HTML in the browser.
  • Screen readers, search engines, and browsers all rely on correct HTML structure to work properly.
  • It's the fastest language to see results in: write a file, open it in a browser, done.

→ Your first HTML file

<!-- index.html -->
<!DOCTYPE html>
<html>
  <head>
    <title>My First Page</title>
  </head>
  <body>
    <h1>Hello, world!</h1>
  </body>
</html>
Try it: save this as index.html and open it by double-clicking the file. No server, no install — that's the beauty of HTML.

Exercise 1.1

Create index.html with a heading containing your name and a paragraph describing why you're learning to code.
Quiz: What does HTML stand for, and what is it NOT responsible for?
HyperText Markup Language. It is not responsible for styling (CSS) or behavior/interactivity (JavaScript) — only structure and meaning.
CHAPTER 02

What HTML Is & How It Works

Tags, elements, the DOM, and what the browser actually does with your markup.

→ Tags vs. Elements

A tag is the markup itself, like <p>. An element is the tag plus its content and closing tag: <p>Hello</p>. Most elements have an opening and closing tag; some, called void elements, don't (<img>, <br>, <input>).

TermExampleMeaning
Tag<p>The markup marker itself
Element<p>Text</p>Opening tag + content + closing tag
Attributeclass="intro"Extra info attached to an opening tag
Void element<img>Self-closing, holds no inner content

→ How a browser turns HTML into a page

HTML file
   │
   ▼
Browser parses text  →  builds the DOM (Document Object Model)
   │                        a tree of nodes representing every element
   ▼
CSS is applied to the DOM (the "how it looks")
   │
   ▼
JavaScript can read/change the DOM (the "how it behaves")
   │
   ▼
Pixels on screen

The DOM is the key idea: your HTML isn't just text, it becomes a tree structure in memory that CSS and JavaScript both operate on. This is why nesting and structure matter so much.

Exercise 2.1

Open any website, right-click → "Inspect", and find the DOM tree in the Elements panel. Identify 3 elements and their attributes.
Quiz: What is the DOM?
A tree-like in-memory representation of the HTML document that the browser builds after parsing, which CSS and JavaScript can then read and modify.
CHAPTER 03

HTML Document Structure

<!DOCTYPE>, <html>, <head>, <body> — the skeleton every page shares.

<!DOCTYPE html>              <!-- tells browser: use modern HTML5 rules -->
<html lang="en">              <!-- root element, wraps everything -->
<head>                        <!-- metadata, not visible content -->
  <meta charset="UTF-8">
  <title>Page Title</title>
</head>
<body>                        <!-- everything visible on the page -->
  <h1>Visible content</h1>
</body>
</html>
PiecePurpose
<!DOCTYPE html>Not a tag — a declaration telling the browser to render in standards mode (HTML5). Must be the very first line.
<html>The root element. The lang attribute helps screen readers and search engines.
<head>Holds metadata: title, character encoding, CSS/JS links, favicon, SEO tags. Nothing here is shown directly.
<body>Holds everything the user actually sees on the page.
Common mistake: forgetting <!DOCTYPE html> triggers "quirks mode," where old, inconsistent rendering rules kick in — layouts break in subtle ways.

CHAPTER 04

Headings & Paragraphs

The backbone of readable, well-structured content.

<h1>Main Page Title</h1>
<h2>Section Heading</h2>
<h3>Sub-section</h3>
<p>A paragraph of body text goes here.</p>
TagPurposeBest practice
<h1>–<h6>Headings, in decreasing importanceUse exactly one <h1> per page; never skip levels (h2 → h4)
<p>A paragraph of textDon't use for spacing — use CSS margins
Common mistake: choosing heading tags by how big they look rather than by document outline. Fix the hierarchy in CSS, not by picking a smaller heading tag.
Quiz: How many <h1> tags should a well-structured page usually have?
One — it represents the page's main title, and both accessibility tools and search engines rely on this being unique.

CHAPTER 06

Comments

Leaving notes in your code that browsers ignore.

<!-- This is a comment, it won't be shown on the page -->
<p>Visible text</p>
<!--
  Multi-line comments
  work the same way
-->
  • Use comments to explain why, not restate the obvious.
  • Handy for temporarily disabling a block of markup while testing.
  • Never put sensitive information in comments — anyone can view page source.
Common mistake: comments cannot be nested — a --> inside another comment closes it early and breaks the rest of the page.
Quiz: Are HTML comments visible in "View Page Source"?
Yes — comments are only hidden from the rendered page, not from the raw source. Never store secrets in them.

Links & Navigation

Connecting pages with <a>.

<a href="https://example.com">External link</a>
<a href="about.html">Relative link</a>
<a href="#pricing">Jump to section</a>
<a href="mailto:hi@example.com">Email us</a>
<a href="tel:+911234567890">Call us</a>
<a href="https://example.com" target="_blank" rel="noopener noreferrer">New tab</a>
AttributePurpose
hrefDestination — URL, relative path, anchor (#id), mailto:, tel:
target="_blank"Opens in a new tab — always pair with rel="noopener" for security
downloadForces the browser to download the file instead of navigating
titleTooltip text shown on hover
Common mistake: using target="_blank" without rel="noopener" — the new tab can access the opening page via window.opener, a real security risk.

CHAPTER 08

Images & Image Attributes

<img>, responsive images, and why alt is never optional.

<img src="cat.jpg" alt="Orange tabby cat sleeping on a windowsill"
     width="400" height="300" loading="lazy">

<!-- responsive: browser picks the best size -->
<img srcset="small.jpg 480w, large.jpg 1024w"
     sizes="(max-width: 600px) 480px, 1024px"
     src="large.jpg" alt="Product photo">
AttributePurpose
srcImage file path/URL
altText alternative — read by screen readers, shown if the image fails to load, used by search engines. Use alt="" only for purely decorative images.
width / heightReserves space before the image loads, preventing layout shift
loading="lazy"Defers loading off-screen images for performance
srcset / sizesServe different image sizes to different screens
Common mistake: writing alt="image" or alt="IMG_2931.jpg" — meaningless alt text is functionally the same as missing alt text.
Quiz: When should alt="" (empty) be used?
Only for purely decorative images that add no information — this tells screen readers to skip the image entirely rather than reading a filename.

Lists: Ordered, Unordered, Description

Grouping related items with the right kind of list.

<!-- Unordered: order doesn't matter -->
<ul>
  <li>Milk</li>
  <li>Eggs</li>
</ul>

<!-- Ordered: sequence matters -->
<ol>
  <li>Preheat oven</li>
  <li>Mix batter</li>
</ol>

<!-- Description list: term/definition pairs -->
<dl>
  <dt>HTML</dt>
  <dd>HyperText Markup Language</dd>
</dl>
TagUse for
<ul> / <li>Unordered lists — bullets
<ol> / <li>Ordered lists — numbered, sequence matters (use start or reversed attributes to customize)
<dl>/<dt>/<dd>Term-definition pairs — glossaries, FAQs, key-value data
Common mistake: nesting lists incorrectly — a nested <ul> must live inside an <li>, not as a sibling of one.

    <tr><td>Total</td><td colspan="2">270</td></tr>

Tag/AttrPurpose

CHAPTER 11

Forms — Every Input Type

How the web collects information from people.

<form action="/submit" method="POST">
  <label for="email">Email</label>
  <input type="email" id="email" name="email" required>

  <button type="submit">Send</button>
</form>

Every input needs a <label> linked via for/id — this is both an accessibility requirement and a usability win (clicking the label focuses the field).

→ Beyond <input>

→ Key attributes

AttributePurpose

Quiz: What's the difference between disabled and readonly?
A disabled field can't be focused or edited AND its value is not sent on submit. A readonly field can't be edited but its value IS still submitted.

CHAPTER 12

Buttons

Three ways to make something clickable — and why they aren't interchangeable.

<button type="submit">Submit form</button>
<button type="button" onclick="doSomething()">Run a script</button>
<button type="reset">Clear form</button>
typeBehavior
submit (default inside a form)Submits the enclosing form
buttonDoes nothing by itself — used with JavaScript
resetResets all fields in the form to their default value
Common mistake: a <button> inside a <form> defaults to type="submit" — a "Cancel" or "Show more" button without an explicit type="button" will unexpectedly submit the form.
Best practice: for navigation ("go to another page"), use <a href="..."> styled as a button, not a real <button> — buttons are for actions, links are for navigation.

CHAPTER 14

YouTube Embedding via iframe

Embedding third-party content safely.

<iframe width="560" height="315"
  src="https://www.youtube.com/embed/VIDEO_ID"
  title="YouTube video player"
  frameborder="0"
  allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture"
  allowfullscreen>
</iframe>
  • Use the /embed/ URL path from YouTube's "Share → Embed" option, not the normal watch URL.
  • Always include a title attribute — screen readers announce it to describe the frame's content.
  • Wrap the iframe in a container with aspect-ratio CSS to keep it responsive across screen sizes.
Common mistake: hardcoding a fixed pixel width/height with no responsive wrapper — the video overflows on mobile screens.

CHAPTER 15

Semantic HTML5 Tags

Structuring a page so its meaning is obvious to browsers, search engines, and screen readers.

<header> ... </header>
<nav> ... </nav>
<main>
  <section>
    <article> ... </article>
  </section>
  <aside> ... </aside>
</main>
<footer> ... </footer>
TagRepresents
<header>Intro content for a page or section — logo, title, nav
<nav>Major navigation links
<main>The single dominant content of the page — one per page
<section>A thematic grouping of content, usually with its own heading
<article>Self-contained content that could stand alone (blog post, news story, product card)
<aside>Tangential content — sidebars, pull quotes, related links
<footer>Closing content for a page or section — copyright, links
Why it matters: semantic tags give screen readers "landmarks" to jump between (skip to nav, skip to main), and help search engines understand which content is the actual article vs. a sidebar.
Quiz: What's the difference between <section> and <article>?
An <article> is self-contained and would make sense distributed on its own (like an RSS feed item). A <section> is just a thematic grouping within the current page and doesn't need to stand alone.

The two generic containers — and when semantic tags should replace them.

<div><span>
Display typeBlock (takes full width, starts new line)Inline (flows with surrounding text)

CHAPTER 20

Linking CSS & JavaScript

Bringing style and behavior into an HTML page.

<!-- in <head>: external CSS -->
<link rel="stylesheet" href="styles.css">

<!-- inline <style> block -->
<style>
  body { font-family: sans-serif; }
</style>

<!-- near end of <body>: external JS -->
<script src="app.js" defer></script>
AttributePurpose
deferDownloads the script in the background, runs it after the HTML is fully parsed — keeps the page from freezing while loading
asyncDownloads and runs as soon as it's ready, possibly before parsing finishes — best for independent scripts (ads, analytics)
Best practice: put CSS <link> tags in <head> so styles are ready before paint; put JS <script> tags with defer so they don't block rendering.

Accessibility Basics

Markup that works for everyone, including screen reader and keyboard users.

TechniqueWhy it matters
Meaningful alt textScreen readers announce it in place of the image
<label> for every inputScreen readers announce what a field is for
Semantic tags (header, nav, main...)Creates navigable "landmarks" for assistive tech
Logical heading orderScreen reader users often navigate by jumping between headings
aria-labelNames an element when there's no visible text label (e.g. icon-only button)
aria-hidden="true"Hides purely decorative elements from assistive tech
Visible focus statesKeyboard users need to see which element is focused
Sufficient color contrastText must be readable for low-vision users
<!-- icon-only button needs a label -->
<button aria-label="Close dialog">✕</button>
Rule of thumb: if you can complete every task on the page using only Tab, Enter, and a screen reader, you're most of the way to accessible.
Quiz: When should you reach for an ARIA attribute instead of a native HTML element?
Only as a last resort — a native <button> is already keyboard-accessible and announced correctly; ARIA is for filling gaps native HTML can't cover, like custom widgets.

CHAPTER 25

Responsive HTML Best Practices

Markup decisions (not just CSS) that make pages work across screen sizes.

  • Always include <meta name="viewport" content="width=device-width, initial-scale=1.0">.
  • Use srcset/sizes on images instead of one oversized image for every screen.
  • Prefer relative units in linked CSS (%, rem, vw) over fixed pixels for layout containers.
  • Structure content so it still makes sense read top-to-bottom on a narrow screen (mobile-first thinking).
  • Avoid fixed width/height on containers that should flex; use them only on images/video to reserve space.
Best practice: design and write your HTML mobile-first, then progressively enhance the layout for larger screens — it's far easier than trying to shrink a desktop layout down later.

CHAPTER 28

HTML Interview Questions

Beginner to advanced — with answers.

→ Beginner

What is semantic HTML and why does it matter?
HTML that describes meaning, not just appearance (e.g. <nav> vs a plain <div>). It improves accessibility, SEO, and code readability.
What's the difference between an HTML element and a tag?
A tag is the markup marker (<p>); an element is the tag plus its content and closing tag.
What are void/self-closing elements? Name three.
Elements with no closing tag or content: <img>, <br>, <input>, <hr>, <meta>.
What does the DOCTYPE declaration do?
Tells the browser to render the page in standards mode (HTML5) instead of legacy "quirks mode."

→ Intermediate

What's the difference between <section> and <div>?
<section> carries semantic meaning (a thematic grouping, usually with a heading); <div> is purely a generic, meaningless container.
How do srcset and sizes improve image performance?
They let the browser choose the most appropriately-sized image file for the current viewport/DPI instead of always downloading one large file.
What's the difference between async and defer on a <script>?
defer waits until HTML parsing finishes and preserves execution order; async runs as soon as the script downloads, potentially before parsing finishes and out of order relative to other scripts.
Why should a form input always have an associated <label>?
For accessibility (screen readers announce the label) and usability (clicking the label focuses the input) — placeholder text is not a substitute.

→ Advanced

How does the browser build the DOM from HTML, and how does that relate to the CSSOM and render tree?
The browser tokenizes and parses HTML into the DOM tree; CSS is parsed into the CSSOM; the two are combined into a render tree that determines what's actually painted, skipping non-visual nodes.
What accessibility tree considerations matter when building a custom widget with divs and ARIA instead of native elements?
You must manually replicate all native behavior: keyboard operability, focus management, correct roles/states via ARIA, and announce changes — native elements provide all this for free, which is why they're preferred when available.
Why can content-visibility or lazy-loading strategies at the markup level affect Core Web Vitals?
Deferring offscreen images/iframes (loading="lazy") and structuring critical content to render first reduces initial payload and improves metrics like Largest Contentful Paint.
What's the risk of target="_blank" without rel="noopener", and why does it matter for security?
The newly opened page can access window.opener and potentially redirect the original tab to a malicious page (reverse tabnabbing); rel="noopener" severs that connection.
